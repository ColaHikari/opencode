## Grounding-Deltas gegen Spec/Kontrakt (gegen REALEN Code verifiziert, 2026-06-07)

Beim Erden gegen den gemergten Phase-1-Code gefunden — der Plan ist gegen den REALEN Code geschrieben, diese Punkte sind die Abweichungen vom naiven Spec-Lesen:

1. **`answer()` kann 404 NICHT von 409 unterscheiden — der HANDLER muss das tun.** `workflow.answer({id})` (`ENGINE` ~Z.2989-3036) gibt `undefined` für VIER Fälle zurück: unbekannte id, fremdes Directory, terminaler Status, UND „live, aber keine offene Frage / paused ohne pending_question". Der Kontrakt verlangt 404 (unbekannte id) ≠ 409 (keine Frage offen). Lösung im Handler: ZUERST `workflow.get(id)` (directory-scoped, `ENGINE` ~Z.1720) — `undefined` ⇒ 404; existiert ⇒ `workflow.answer(...)` aufrufen, dessen `undefined` ⇒ 409 (`ConflictError`), sonst 200 `{run}`. Diese Reihenfolge ist verifiziert directory-konsistent (beide scopen aufs selbe `directory`).

2. **`ConflictError` (409) existiert bereits** in `ERRORS` (Z.25-32, `{message, resource?}`, `httpApiStatus:409`) — keine neue Fehlerklasse nötig. Es gibt KEINEN `conflict()`-Helper (nur `notFound()` Z.188); `ConflictError` wird direkt instanziiert (`new ConflictError({message, resource})`), und `ApiNotFoundError` via vorhandenem `notFound(...)`-Helper.

3. **Run-Serializer filtert KEINE Felder.** Die HTTP-`get`/`start`-Erfolge geben `Workflow.Run` 1:1 zurück (`GROUP` `success: described(Workflow.Run, ...)`); `Run` trägt `pending_question` bereits als optionales Feld (`ENGINE` Z.225-231). ⇒ Der Spec-Halbsatz „expose `pending_question` if the serializer filters fields" ist ein No-Op: nichts zu tun, das Feld ist schon auf dem Wire. (Verifikation als Assertion in Task 6.)

4. **`StartOptions.invalidate_agents` ist `number[]` (mutable), die HTTP-Decode liefert `readonly number[]`.** Der bestehende `start`-Handler kopiert bereits (`HANDLER` Z.65 `[...ctx.payload.invalidate_agents]`). Am TOOL ist das Parameters-Schema-Array bereits `readonly` nach Decode; vor der Durchreiche an `workflow.start` ⇒ `[...params.invalidate_agents]` spreaden (Task 1).

5. **`resume_of` ist `Workflow.RunID` (branded).** Der `decodeRunId(raw)`-Guard im TOOL (Z.303-305) liefert `Workflow.RunID | undefined` (prefix-`"job"`-Guard, kein Throw). QW3 nutzt diesen vorhandenen Guard; ein malformer `resume_of` ⇒ klarer Fehler statt Defect (Task 1).

6. **Inline-`source` am `start`: das Tool hat `source` BEREITS als Parameter** (`TOOL` Z.62-64) — aber nur `create` nutzt es; `start` ignoriert es heute. P3 fügt den `start`-Zweig hinzu. Die Engine kennt `temporary` + `source` auf `StartOptions` (Z.294-295) und `startWorkflow(input)` nimmt `source`/`temporary` schon (`TOOL` Z.355-381) → die temporäre Variante reicht `temporary:true` + `source` + den aus dem Source gelesenen Meta-Namen durch. `start` + `source` ist **mutually exclusive mit `name`** (Spec §5.1): genau eins muss gesetzt sein.

7. **Das Tool hat HEUTE KEINE hartkodierte Agent-Liste** (general/build/plan/explore). Grep über `TOOL` findet keine solche Liste; die `DESCRIPTION` (Z.71-80) erwähnt keine Agent-Namen, und es gibt keinen `create`-Guidance-Text mit Agent-Namen. QW7 ist daher ein ADDITIV: Live-Roster aus `Agent.Service` in `read`- und `create`-Ausgabe AUFNEHMEN (es gibt nichts „hartkodiertes zu ersetzen"). `Agent.Service` ist im TOOL noch NICHT importiert → zur Tool-Layer hinzufügen. `Agent.Info` (`agent.ts` Z.30-51) trägt `{name, description?, mode, hidden?}`; Roster filtert `hidden !== true` und `mode !== "primary"` (subagent-/all-dispatchbar) und sortiert nach `name`.

8. **`whenToUse` lebt NOCH NICHT in `META`/`PLUGIN`/`fmt`** (grep bestätigt: nur Agent-Generierung nutzt das Wort). QW4 fügt `whenToUse?: string` additiv hinzu — `META.Meta`-Struct, `PLUGIN.workflow()`-Helper-Typ + Mapping, der `fmt`-`<available_workflows>`-Renderer (`ENGINE` Z.1578-1607) und die Tool-`read`-Ausgabe (`formatWorkflow`, `TOOL` Z.125-144). Kein TUI-Approval-Dialog in DIESEM Track (das ist T-TUI; QW4-Hinweis auf den Dialog ist track-fremd). SDK-Regen ist Phase 3 (NICHT hier).

9. **`answer`-Tool-Action: NICHT in Scope.** Spec §5.1 listet nur `resume_of`/`invalidate_agents` als neue Tool-Parameter — KEINE `answer`-Action/Parameter am Tool. Die HTTP-`answer`-Route bedient TUI/HTTP-Konsumenten; das Modell beantwortet Fragen NICHT über dieses Tool. YAGNI: nicht bauen.
