### Task 2 (DOCUMENTED FALLBACK): question → ACP-Permission/Elicitation-Spiegelung

> Per Spec §5.3 Rückfall-Klausel als **Findings & Fallback** geschrieben — KEINE TDD-Steps, weil das Feature in diesem Track nicht gebaut wird.

**Was wurde gegroundet:**

- Ein workflow-`pending_question` entsteht in der Engine (Phase 1, Master-Kontrakt: `ctx.question` → `pending_question`-Spalte + `workflow.run.updated`-Event mit `pending_question: boolean`). Es ist KEIN Session-Permission-Event.
- Der ACP-Event-Bridge (`acp/event.ts:72-82`) behandelt exakt drei Bus-Event-Typen: `permission.asked`, `message.part.updated`, `message.part.delta`. Es gibt **keinen** Handler für `workflow.run.updated`/`workflow.run.finished`. Eine Spiegelung müsste also (i) einen neuen Workflow-Event-Handler in der `Subscription` ergänzen UND (ii) die Frage an eine ACP-Session koppeln.
- ACP **hat** ein Elicitation-Primitiv: `AgentSideConnection.createElicitation` (`@agentclientprotocol/sdk` `dist/acp.d.ts:95`), Request/Response in `schema/types.gen.d.ts:914-960`. **Aber** es ist im SDK-Header explizit als **„UNSTABLE … not part of the spec yet, and may be removed or changed at any point" / `@experimental`** markiert (`schema/types.gen.d.ts:902-912` für den Request, `1318-1326` für die Form-Capabilities). Es wird in opencode **nirgends** verdrahtet (`grep -rn createElicitation packages/opencode/src` = leer), die Client-Capability `elicitation` wird in `initialize` (`S:93-138`) **nicht** advertised, und `createElicitation` ist **nicht** Teil des `ServiceConnection`-Picks (`S:53-54`).
- Das stabile Alternativ-Primitiv `requestPermission` (`acp/permission.ts:63-75`) ist **tool-call-förmig**: es verlangt ein `toolCall` mit `toolCallId`, `kind`, `rawInput`, `locations` und liefert nur eine `once/always/reject`-Auswahl zurück (`permission.ts:16-20`) — es transportiert keine Freitext-Antwort und keine Options-Liste, die `ctx.question({question, options?})` braucht.

**Warum deferred (Begründung der Klassifikation):**

1. **Falsches Trägersignal / falsche Session.** Die Frage wird auf der Workflow-Run-Session (bzw. deren Child) gestellt — einer Session, die der ACP-Store **nicht kennt** (siehe Task 3). Selbst ein Handler im Event-Bridge könnte die Frage keiner ACP-Session zuordnen (`event.ts`-Handler returnen bei `!session`). Task 2 ist also durch denselben Store-Limit blockiert wie Task 3.
2. **YAGNI/Stabilität.** Das einzige passend-geformte Primitiv (`createElicitation`, Freitext+Form+Options) ist ausdrücklich instabil/experimentell und kann „at any point" entfernt werden — ein Feature darauf zu gründen widerspricht der YAGNI-/Robustheits-Disziplin des Mega-PR. Das stabile `requestPermission` passt semantisch nicht (kein Freitext, keine Options).
3. **Spec erlaubt es.** Spec §5.3: „question-Events als ACP-Permission-Request gespiegelt" mit der Rückfall-Klausel „liefert der Track Discovery-only und dokumentiert den Rest (kein PR-Blocker)". Master §9 nennt denselben Rückfall.

**Limitierende Stellen (file:line):**

- `acp/service.ts:53-54` — `ServiceConnection` exportiert weder `createElicitation` noch ein Freitext-Permission-Surface.
- `acp/service.ts:93-138` — `initialize` advertised keine `elicitation`-Capability; ohne Advertise darf der Agent laut ACP `createElicitation` nicht nutzen.
- `acp/event.ts:72-82` — Event-Dispatch kennt keinen `workflow.run.updated`-Case.
- `@agentclientprotocol/sdk` `schema/types.gen.d.ts:902-912` — `CreateElicitationRequest` ist UNSTABLE/@experimental.

**Future-Change-Skizze (für einen späteren, eigenständigen PR — NICHT hier):**

1. Sobald ACP-Elicitation stabilisiert ist (Capability-Flag im SDK ohne `@experimental`): in `initialize` `agentCapabilities`/Client-Negotiation um `elicitation` erweitern und `createElicitation` zum `ServiceConnection`-Pick (`S:53`) hinzufügen.
2. Voraussetzung: Task 3 (Store-Adoption) muss zuerst gelöst sein, damit die Workflow-(Child-)Session eine ACP-`sessionId` hat, an die die Elicitation gebunden werden kann.
3. Dann im Event-Bridge einen `workflow.run.updated`-Handler ergänzen: bei `pending_question === true` den Run via `sdk.workflow.get(runId)` lesen, `pending_question.{question, options?}` in eine `CreateElicitationRequest` (`mode:"form"`, `message: question`) übersetzen, und die Antwort via der in T-Tool fixierten Route `POST /workflow/run/:id/answer` (`{answer}`) zurückspielen. Mapping `decline/cancel` → kein Answer (Run bleibt `paused`/läuft in Timeout).

### Task 3 (DISCOVERY-ONLY FALLBACK): Subagent-Streaming in den ACP-Store

> Per Spec §5.3 Rückfall-Klausel + explizite Plan-Anweisung als **Findings & Fallback** — KEINE TDD-Steps. Verdikt: **nicht lieferbar ohne invasive Store-Änderung; gedroppt.**

**Was wurde gegroundet (der Streaming-Pfad heute):**

- Der ACP-Event-Bridge streamt Tool-Calls/Thoughts, indem er Bus-Events (`message.part.updated`, `message.part.delta`, Tool-States) auf `connection.sessionUpdate(...)` mappt (`acp/event.ts:136-336`). Tool-Lifecycle: `tool_call` (pending) → `tool_call_update` (running/completed/error) (`event.ts:243-336`). Thoughts: `agent_thought_chunk` (`event.ts:101,191-203`).
- **Jeder** dieser Handler gated strikt auf eine dem ACP-Store bekannte Session:
  - `handlePartUpdated` (`event.ts:136-157`): `const session = await … this.input.session.tryGet(sessionId); if (!session) return` (`:139-140`).
  - `handlePartDelta` (`event.ts:159-204`): identisches `tryGet`+early-return (`:161-162`).
- Der ACP-Store (`acp/session.ts:96-201`) ist eine `Map<string, Info>` und wird **ausschließlich** über die `create`/`load`-Methoden befüllt, die NUR aus den Protokoll-Handlern `newSession`/`loadSession`/`resumeSession`/`forkSession` aufgerufen werden (`S:185,222,307,378`). Es gibt **keine** `adopt`/`attach`/`register`-API und keinen Parent-Walk (`grep -rn "adopt\|attach\|parentID" packages/opencode/src/acp/` = leer).
- Die Workflow-Child-Sessions erzeugt die **Engine** selbst via `sessions.create({ parentID: <run.session_id>, title, agent, model, permission, directory })` (`workflow/workflow.ts:2376-2383`) und trackt sie engine-seitig in `active.sessions.add(session.id)` (`:2388`) — rein für cancel/abort, nicht im ACP-Store. Sie haben ein echtes `parentID` (auch über die opencode-SDK sichtbar: `session.gen` `parentID?`, `packages/sdk/js/src/v2/gen/types.gen.ts:176`), aber das ACP-Bus-Event trägt nur die **eigene** `sessionID` der Child-Session, kein Parent.

**Feasibility-Verdikt (klar, wie verlangt):** **Der Store kann engine-erzeugte Child-Sessions NICHT adoptieren.** Er keyt strikt auf die ACP-initiierte Session; es existiert kein Adoptions-Seam. Damit verwirft der Bridge jedes Streaming-Event einer Workflow-Child-Session (unbekannte `sessionID` → early-return). Streaming wäre nur durch eine **invasive** Änderung erreichbar (siehe Skizze) — die ist per Rückfall-Klausel ausdrücklich zu vermeiden; der Task wird **gedroppt**.

**Limitierende Stellen (file:line):**

- `acp/event.ts:139-140` und `acp/event.ts:161-162` — `tryGet`+early-return verwerfen alle nicht-Store-Sessions (das harte Limit).
- `acp/session.ts:61-90` (Interface) / `:168-200` (Impl) — keine Adoptions-/Register-Methode; nur `create`/`load` via Protokoll.
- `acp/service.ts:185,222,307,378` — die einzigen `session.create`/`session.load`-Aufrufe; alle aus Protokoll-Handlern.
- `workflow/workflow.ts:2376-2388` — Child-Session-Erzeugung + engine-seitiges Tracking (außerhalb des ACP-Stores).

**Future-Change-Skizze (für einen späteren, eigenständigen, größeren PR — NICHT hier):**

3. **`workflow.list`-Directory-Scope:** Bestätigen, dass `sdk.workflow.list({ directory })` dieselbe Directory-Semantik wie `command.list`/`skills` in `loadDirectorySnapshot` nutzt (alle teilen `directory`), damit Discovery directory-korrekt bleibt.
